Infrastruttura.

componente 01

Zobrist Hashing

Come fa il motore a riconoscere se una posizione è già stata analizzata? Lo Zobrist Hashing assegna un numero a 64 bit a ogni configurazione della scacchiera combinando con XOR i valori random precalcolati per ogni (pezzo × casella).

Il risultato è un hash quasi unico: due posizioni diverse producono (quasi sempre) hash diversi, mentre la stessa posizione raggiunta per percorsi diversi produce sempre lo stesso hash. L'aggiornamento incrementale — rimuovendo XOR del pezzo partenza e aggiungendo quello destinazione — rende il calcolo velocissimo.

zobrist.cpp C++ 
// Tabella random 64-bit: [tipo_pezzo][casella][colore]
uint64_t ZOBRIST[6][64][2];

void init_zobrist() {
    for (auto& p : ZOBRIST) for (auto& s : p) for (auto& v : s)
        v = rand64();  // numeri pseudo-casuali a 64 bit
}

// Aggiornamento incrementale dopo una mossa
void aggiorna_hash(uint64_t& hash, Mossa m) {
    hash ^= ZOBRIST[m.pezzo][m.da][m.colore];   // rimuovi partenza
    hash ^= ZOBRIST[m.pezzo][m.a][m.colore];    // aggiungi destinazione
    if (m.cattura) hash ^= ZOBRIST[m.cattura][m.a][!m.colore];
}

// L'aggiornamento XOR è O(1) — indipendente dal numero di pezzi
// Ricalcolo completo sarebbe O(32) — usato solo all'inizializzazione
🎲
Perché XOR funziona perfettamente
Lo XOR ha due proprietà fondamentali: A XOR A = 0 (rimuovere un pezzo è l'operazione inversa di aggiungerlo) e A XOR B = B XOR A (l'ordine non conta). Questo garantisce che lo stesso insieme di pezzi produca sempre lo stesso hash, indipendentemente dall'ordine in cui sono stati piazzati.
componente 02

Tabella Trasposizioni (TT)

La Tabella Trasposizioni è una cache hash di dimensione fissa (tipicamente 128–256 MB) che memorizza i risultati delle ricerche già effettuate. Quando il motore incontra una posizione già analizzata — raggiunta per un percorso diverso, da qui il nome "trasposizione" — può riusare il risultato invece di ricalcolarlo.

Ogni entry conserva: hash Zobrist, profondità, valore, tipo (esatto / lower bound / upper bound) e mossa migliore (usata per l'ordinamento).

transposition_table.cpp C++ 
struct TTEntry {
    uint64_t hash;    // chiave Zobrist per verifica collisioni
    int16_t  valore;  // risultato della ricerca
    uint8_t  depth;   // profondità a cui è stato calcolato
    uint8_t  tipo;    // EXACT=0, LOWER=1, UPPER=2
    Mossa    best;    // mossa migliore trovata (per l'ordinamento)
};

// Lookup nella TT — O(1)
TTEntry* tt_lookup(uint64_t hash) {
    return &TT[hash % TT_SIZE];
}

// Utilizzo nella ricerca
TTEntry* entry = tt_lookup(s.hash);
if (entry->hash == s.hash && entry->depth >= prof)
{
    if (entry->tipo == EXACT)  return entry->valore;   // hit esatto
    if (entry->tipo == LOWER && entry->valore >= beta)  return beta;
    if (entry->tipo == UPPER && entry->valore <= alfa)  return alfa;
}
componenti 03–04

IID & Countermove Heuristic

03
Internal Iterative Deepening
Mossa TT mancante? IID la trova
Quando un nodo non ha una mossa TT disponibile (miss in tabella), l'ordinamento delle mosse peggiora drasticamente. IID esegue una ricerca superficiale (prof - 2) per trovare una mossa "buona" da usare come prima candidata.

Il costo di IID è ammortizzato: la mossa trovata migliora abbastanza l'ordinamento da far guadagnare più tempo di quante ne costa.
04
Countermove Heuristic
La risposta alla mossa precedente
La Countermove Heuristic memorizza, per ogni mossa dell'avversario, quale mossa del giocatore corrente ha causato un cutoff nell'ultima volta che quella mossa avversaria è stata vista.

Nella struttura contromossa[pezzo][casella], GMVT conserva la risposta vincente e la propone prima nell'ordinamento — spesso causando cutoff early.
iid_countermove.cpp C++ 
// IID: se non c'è mossa TT, fai una ricerca superficiale
Mossa mossa_tt = tt_best(s.hash);
if (!mossa_tt.valida() && prof >= 6)
{
    minimax(s, prof - 2, alfa, beta);  // IID: cerca a prof-2
    mossa_tt = tt_best(s.hash);       // ora la TT ha una mossa
}

// Countermove Heuristic: aggiorna dopo un cutoff
if (val >= beta && !e_cattura(mossa))
{
    contromossa[mossa_prev.pezzo][mossa_prev.dest] = mossa; // memorizza
}

// Ordinamento: la contromossa viene proposta subito dopo killer e TT
if (mossa == contromossa[prev.pezzo][prev.dest])
    score_ord += 9000;  // alta priorità nell'ordinamento
componente 05

Regola 50 Mosse & Ripetizioni

Il motore deve riconoscere le situazioni di patta per non valutare erroneamente posizioni che terminano in pareggio. GMVT gestisce due casi distinti:

Regola delle 50 mosse: se per 50 mosse consecutive non è stata fatta una cattura né una mossa di pedone, la partita è patta. Il contatore half_move_clock viene azzerato a ogni cattura/mossa pedone.

Triplice ripetizione: se la stessa posizione compare tre volte nella partita (con le stesse possibilità di arrocco ed en passant), è patta. GMVT usa lo stack degli hash Zobrist per rilevare le ripetizioni in O(d).
// CONTATORE HALF-MOVE CLOCK
0 / 100
0 (mossa pedone/cattura) 100 = PATTA ⚑
🕐
Contatore a zero. Gioca alcune mosse silenzose.
draw_detection.cpp C++ 
// Controllo patta all'inizio di ogni nodo
int minimax(Scacchiera& s, int prof, int alfa, int beta)
{
    // Regola 50 mosse
    if (s.half_move_clock >= 100) return 0;  // patta!

    // Rilevamento ripetizioni: scansiona lo stack degli hash
    for (int i = ply - 2; i >= 0; i -= 2) {
        if (hash_stack[i] == s.hash) return 0;  // ripetizione!
        if (hash_stack[i] == reset_hash) break; // pedone/cattura → stop
    }

    // ... continua la ricerca normale
}
componente 06

Opening Book

Nelle primissime mosse di apertura, la ricerca non è il modo migliore per scegliere: le posizioni sono troppo equilibrate e la profondità necessaria per distinguere le varianti sarebbe enorme. L'Opening Book di GMVT contiene ~60 linee di apertura codificate come sequenze di hash Zobrist → mossa.

Il motore consulta il libro nelle prime mosse e risponde immediatamente, senza sprecare tempo di calcolo in posizioni teoricamente consolidate.

opening_book.cpp C++ 
// Book: mappa hash Zobrist → mossa (precompilata)
static const std::unordered_map<uint64_t, Mossa> OPENING_BOOK = {
    { 0xA4B3C2D1E0F19283, mossa("e2e4") },  // pos. iniziale → e4
    { 0x3F7E1A2B4C5D6E7F, mossa("d2d4") },  // pos. iniziale → d4 (alt.)
    { 0x1B2C3D4E5F607182, mossa("g1f3") },  // dopo 1.e4 e5 → Nf3
    // ... ~60 linee totali
};

Mossa cerca_book(uint64_t hash) {
    auto it = OPENING_BOOK.find(hash);
    return (it != OPENING_BOOK.end()) ? it->second : Mossa();
    // Se non trovato → mossa nulla → ricerca normale
}
📖
Book lookup in O(1)
Il lookup nell'opening book è basato sull'hash Zobrist della posizione corrente: O(1) con l'unordered_map. GMVT usa il book finché la posizione è nel database; appena esce dalle linee conosciute, attiva la ricerca normale. L'hash Zobrist già calcolato viene riusato, senza costo aggiuntivo.
